# 코드로 배우는 video_player — 소스코드 가이드

이 문서는 `video_player` 의 소스코드를 **교육용**으로 설명합니다. 한 편의 이야기로,
`player video.mp4` 한 줄을 실행했을 때 코드가 어떤 순서로 움직이는지 따라가며
각 부분의 역할과 "왜 이렇게 만들었는가"를 풀어 놓았습니다.

## 들어가며

**누구를 위한 글인가** — Python 문법은 어느 정도 알지만, 이 프로젝트의 도메인
(mpv·DRM·헤드리스 리눅스·계층형 테스트)은 처음인 분. 그래서 Python 문법은 설명하지
않고, 도메인 개념과 설계 의도에 집중합니다.

**이 프로그램이 하는 일** — 데스크톱 환경이 없는(헤드리스) 미니 PC에서, 터미널로
`player <영상파일>` 을 실행하면 화면(HDMI)에 영상을, 스피커로 소리를 내보내고, 키보드로
일시정지·탐색·볼륨·종료를 조작하는 **단발 실행형** 플레이어입니다. 영상이 끝나거나
`q` 를 누르면 깔끔히 종료하고 터미널로 돌아옵니다.

**읽는 법** — 2장에서 큰 그림을, 3장에서 낯선 용어를 먼저 짚고, 4장에서 실제 실행
흐름을 따라갑니다. 4장이 본론입니다. 코드 인용은 실제 소스(`src/video_player/`)와
같으며, 파일·식별자 이름을 그대로 씁니다.

## 2. 큰 그림 (아키텍처)

프로그램은 **한 방향으로만** 흐릅니다. 입력(키보드)이 "무엇을 하라"는 추상적인
*동작(Action)* 으로 바뀌고, 그 동작이 재생 엔진을 거쳐 실제 mpv 명령이 됩니다.

```
   키 입력            추상 동작            재생 명령           실제 디코딩/출력
 ┌──────────┐  Action  ┌────────────┐  메서드  ┌────────┐  libmpv  ┌─────────┐
 │ keyboard │ ───────▶ │ Controller │ ───────▶ │ Player │ ───────▶ │   mpv   │
 │ (입력원) │          │ (분리막)   │          │ (엔진) │          │ FFmpeg  │
 └──────────┘          └────────────┘          └────────┘          └────┬────┘
                                                                        │
                                                              DRM/KMS → HDMI
                                                              (영상 + 음성)
   이 모든 것을 조립하고 실행 루프를 도는 것이 cli.py 입니다.
```

| 구성요소 | 파일 | 한 줄 역할 |
|---|---|---|
| 입력원 | `keyboard.py` | 키 바이트를 추상 `Action` 으로 변환 |
| Controller | `controller.py` | `Action` 을 받아 적절한 `Player` 메서드를 호출 |
| Player | `player.py` | libmpv 를 감싼 재생 엔진 (로드·일시정지·탐색…) |
| 조립/실행 | `cli.py` | 인자 검증 → 부품 조립 → 재생 루프 → 종료 코드 |
| 설정·상수·예외 | `config.py`·`constants.py`·`errors.py` | mpv 옵션, 숫자 상수, 종료 코드 예외 |

> **왜 단방향이고, 왜 굳이 분리했나?**
> `keyboard → Controller → Player → mpv` 는 의존이 한쪽으로만 흐릅니다. 덕분에
> **입력원만 갈아끼우면** 나머지를 그대로 재사용할 수 있습니다. 지금은 키보드지만,
> 나중에 블루투스 리모컨(evdev)이나 프론트엔드(IPC)가 붙어도 "바이트/메시지를
> `Action` 으로 바꾸는 새 입력원"만 만들면 Controller·Player 는 손대지 않습니다.
> 또한 Controller 가 입력원과 Player 사이의 **분리막** 역할을 해서, 키보드 코드가
> mpv 를 직접 건드리지 못하게 막습니다(테스트도 쉬워집니다 — 4.4 참고).

## 3. 도메인 개념 미니 primer

4장을 읽기 전에, 처음 볼 만한 용어를 짧게 정리합니다.

- **헤드리스(headless)** — 모니터에 GUI 데스크톱(예: GNOME)이 없는 상태. 창 관리자도
  없으므로, 우리가 직접 화면에 그려야 합니다.
- **DRM/KMS** — 리눅스 커널이 그래픽 카드와 화면 출력을 다루는 저수준 인터페이스
  (Direct Rendering Manager / Kernel Mode Setting). 데스크톱 없이 **커널을 통해 화면에
  직접** 영상을 띄울 때 씁니다. mpv 의 `vo=gpu` + `gpu-context=drm` 이 이 경로입니다.
- **HDMI** — 그 화면 출력이 나가는 케이블. 영상과 음성이 함께 나갑니다.
- **mpv / libmpv** — mpv 는 강력한 오픈소스 미디어 플레이어이고, `libmpv` 는 그 핵심을
  **라이브러리로** 떼어내 다른 프로그램이 불러 쓰게 만든 것입니다. 우리는 mpv 창을
  띄우는 게 아니라 libmpv 를 우리 프로그램 안에서 엔진처럼 사용합니다.
- **FFmpeg** — mpv 내부에서 실제 코덱을 디코딩하는 엔진. "거의 모든 포맷 재생"의 근거.
- **python-mpv** — libmpv 를 파이썬에서 부르게 해주는 바인딩. `import mpv` 로 씁니다.
  옵션 키의 밑줄(`_`)을 mpv 옵션의 하이픈(`-`)으로 자동 변환해 줍니다.
- **하드웨어 디코딩(VA-API) / 소프트웨어 폴백** — 가능하면 GPU로 디코딩해 CPU·전력을
  아끼고(`hwdec=auto-safe`), 불가능하면 자동으로 CPU(FFmpeg) 디코딩으로 **떨어집니다
  (fallback)**. 그래서 "재생 자체"는 항상 보장됩니다.
- **OSD (On-Screen Display)** — 화면 위에 잠깐 뜨는 정보(⏸ 아이콘, 진행바, 볼륨 등).
  mpv 내장 OSD 를 씁니다.
- **TTY 원시 모드(raw/cbreak)** — 보통 터미널은 Enter 를 눌러야 한 줄을 넘겨주고 입력을
  화면에 그대로 보여줍니다(에코). 게임처럼 **키 하나하나 즉시** 받으려면 이 동작을 꺼야
  하는데, 그 설정을 "원시 모드"라 합니다(리눅스의 `termios`/`tty` 로 제어).
- **종료 코드(exit code)** — 프로그램이 끝나며 OS에 남기는 숫자. `0`=정상, `2`=인자/파일
  오류, `3`=디코드 실패. 나중에 다른 프로그램이 우리를 자식으로 띄울 때 이 숫자로
  성공/실패를 판단합니다.

## 4. 실행 흐름 따라가기

이제 `player video.mp4` 를 실행했다고 보고, 코드를 순서대로 따라갑니다.

### 4.1 진입 — `cli.main`

`player` 라는 명령은 `pyproject.toml` 의 진입점 설정으로 `cli.main` 에 연결됩니다.

```toml
[project.scripts]
player = "video_player.cli:main"
```

`main` 이 하는 일은 단순합니다. (`src/video_player/cli.py`)

```python
def main(argv: list[str] | None = None) -> int:
    setup_logging()
    parser = _build_parser()
    try:
        namespace = parser.parse_args(argv)
    except SystemExit as exc:
        # argparse: 인자 없음/오류 → 사용법 출력 후 코드 2, 도움말(-h) → 0.
        return int(exc.code) if isinstance(exc.code, int) else EXIT_OK

    path = Path(namespace.path)
    try:
        _validate_media_path(path)
    except ArgumentError as exc:
        log.error("%s", exc)
        return exc.exit_code

    return play(path)
```

- **인자 파싱** — `argparse` 가 영상 경로 인자 하나를 받습니다. 인자가 없으면 argparse
  스스로 사용법을 출력하고 `SystemExit(2)` 를 던지는데, 이걸 잡아 종료 코드 2로 돌려줍니다.
- **파일 검증** — `_validate_media_path` 가 존재·종류·읽기 권한을 확인하고, 문제가 있으면
  `ArgumentError`(종료 코드 2)를 던집니다.

```python
def _validate_media_path(path: Path) -> None:
    if not path.exists():
        raise ArgumentError(f"파일을 찾을 수 없습니다: {path}")
    if not path.is_file():
        raise ArgumentError(f"파일이 아닙니다: {path}")
    if not os.access(path, os.R_OK):
        raise ArgumentError(f"파일에 접근할 수 없습니다: {path}")
```

검증을 통과해야 비로소 `play(path)` 로 넘어갑니다.

> **왜 `main` 은 종료 코드를 `return` 하나?**
> `pyproject` 의 console_scripts 진입점은 `sys.exit(main())` 형태로 감싸집니다. 즉
> `main` 이 돌려준 정수가 그대로 프로세스 종료 코드가 됩니다. 그래서 곳곳의 오류를
> `exit_code` 를 가진 예외로 잡아 `return` 하면, 종료 코드 규칙(0/2/3)이 한 곳에서 정리됩니다.

### 4.2 설정 — `Config`

`play()` 는 가장 먼저 `Config` 를 만듭니다. `Config` 는 **mpv 에 줄 옵션들**과 조작 단위
(탐색 5초, 볼륨 5%)를 한곳에 모은 동결 데이터클래스입니다. (`src/video_player/config.py`)

핵심은 `mpv_options()` 가 돌려주는 딕셔너리입니다. 옵션은 세 묶음으로 나뉩니다.

```python
opts: dict[str, Any] = {
    # --- 보안: 우리가 정의한 키만, 외부 스크립트 차단 ---
    "input_default_bindings": "no",
    "input_vo_keyboard": "no",
    "load_scripts": "no",
    "osc": "no",
    # --- 디코딩·프레임 드롭 ---
    "hwdec": self.hwdec,          # "auto-safe": HW 가능하면 쓰고 아니면 SW 폴백
    "framedrop": "vo",
    # --- 디코더 선행 버퍼(SW 디코딩 스파이크 흡수) ---
    "vd_queue_enable": "yes",
    "ad_queue_enable": "yes",
    "vd_queue_max_secs": 15,
    "vd_queue_max_bytes": "2000MiB",
    # --- 압축 데이터 읽기 캐시(I/O 지터 완화) ---
    "cache": "yes",
    "demuxer_max_bytes": "512MiB",
    # --- 출력 ---
    "vo": self.vo,                # "gpu"
    "ao": self.ao,               # "alsa"
    "osd_duration": self.osd_duration_ms,
}
```

- **보안 묶음** — `input_default_bindings=no` 로 mpv 의 기본 키바인딩을 모두 끕니다.
  우리가 정의한 키만 동작하게 하려는 것입니다(스펙 요구사항). `load_scripts=no`,
  `osc=no` 로 외부 스크립트·기본 화면 컨트롤러도 끕니다 — 신뢰할 수 없는 미디어를
  다룰 때 공격 표면을 줄이는 조치입니다.
- **성능 묶음** — `docs/성능_자원_노트.md` 의 정책을 그대로 옮긴 것입니다. SW 디코딩의
  순간 부하를 흡수하려 디코더 선행 버퍼(queue)를 넉넉히 두고, I/O 지터를 위해 읽기
  캐시를 켭니다.
- **출력 묶음** — DRM/KMS 로 HDMI 에 직접 그립니다.

마지막 줄이 살짝 까다롭습니다.

```python
    if opts.get("vo") == "gpu":
        opts["gpu_context"] = self.gpu_context   # "drm"
```

> **왜 `gpu_context` 는 조건부로 넣나?**
> `gpu-context=drm` 은 `vo=gpu` 일 때만 의미가 있고, 다른 출력(`vo=null` 등)에서는
> libmpv 가 **오류로 거부**합니다. 통합 테스트는 화면 없이 `vo=null` 로 돌리는데, 그때도
> 같은 `Config` 를 쓰려면 `vo` 가 `gpu` 가 아닐 때는 `gpu_context` 를 빼야 합니다. 그래서
> override 까지 반영한 *최종* `vo` 를 보고 결정합니다. (이 `overrides` 구멍이 4.x와
> 5장의 테스트를 가능하게 합니다.)

### 4.3 엔진 — `Player` + libmpv  *(핵심)*

`play()` 가 `Player(config)` 를 만들면, 생성자에서 libmpv 가 깨어납니다.
(`src/video_player/player.py`)

```python
import mpv  # libmpv 바인딩 — 이 모듈을 import 하는 순간 libmpv 가 필요해진다

class Player:
    def __init__(self, config: Config, overrides: dict[str, Any] | None = None) -> None:
        self._config = config
        self._mpv = mpv.MPV(**config.mpv_options(overrides))   # 옵션을 splat 으로 전달
        self._end_reason: bytes | None = None
        self._file_error: str | None = None

        @self._mpv.event_callback("end-file")
        def _on_end_file(event: Any) -> None:
            data = event.as_dict()
            self._end_reason = data.get("reason")          # b"eof" / b"error" ...
            file_error = data.get("file_error")
            if isinstance(file_error, bytes):
                self._file_error = file_error.decode(errors="replace")
            ...
        self._mpv.volume = config.initial_volume
```

여기서 두 가지가 중요합니다.

**(1) "재생이 어떻게 끝났는가"를 이벤트로 잡는다.** libmpv 는 파일 재생이 끝날 때
`end-file` 이벤트를 보내는데, 그 `reason` 이 `eof`(정상 끝) 인지 `error`(디코드 실패)
인지를 알려줍니다. 위 콜백이 그 이유를 보관해 둡니다. 나중에 이걸로 정상 종료와
재생 불가를 구분합니다.

```python
    def wait_for_playback(self) -> None:
        self._mpv.wait_for_playback()           # 재생 끝까지 블록
        if self._end_reason == _REASON_ERROR:    # b"error"
            detail = self._file_error or "알 수 없는 디코드 오류"
            raise DecodeError(detail)            # → 종료 코드 3
        log.info("재생 정상 종료(EOF).")
```

> **왜 깨진 파일에 `DecodeError` 를 던지나?**
> 스펙의 핵심 요구는 "재생 불가 파일에서 **멈추지(hang) 말고**, 명확한 로그를 남기고
> 정상 종료(코드 3)" 입니다. `wait_for_playback()` 은 깨진 파일에서도 예외 없이
> *돌아오기만* 하므로, 우리가 `reason` 을 직접 확인해 `DecodeError` 로 바꿔줍니다.
> 이 예외는 `errors.py` 에서 `exit_code = 3` 을 들고 있어, 결국 종료 코드 3이 됩니다.

**(2) 조작 메서드와 OSD.** Controller 가 부를 메서드들이 여기 있습니다.

```python
    def pause(self) -> None:
        self._mpv.pause = True
        self._safe_command("show-text", "⏸", self._config.osd_duration_ms)

    def seek(self, delta: float) -> None:
        # 키프레임 모드 탐색(빠름). 경계는 mpv 가 0~끝으로 클램프한다.
        self._safe_command("seek", delta, "relative+keyframes")
        self._safe_command("show-progress")
```

각 조작 뒤에 `show-text`/`show-progress` 로 OSD 를 잠깐 띄웁니다. `_safe_command` 는
이런 보조 명령을 `try/except` 로 감싸서, 종료 직전처럼 mpv 가 명령을 못 받는 상황에서도
**재생 자체가 깨지지 않게** 예외를 삼킵니다.

> **왜 파일 경로를 셸이 아니라 인자로 넘기나?**
> `self._mpv.play(target)` 처럼 python-mpv 는 셸을 거치지 않고 libmpv 에 직접 넘깁니다.
> 즉 파일명에 이상한 문자가 있어도 **셸 인젝션**이 생기지 않습니다(스펙 보안 가이드).

> **왜 `import mpv` 가 이 파일 맨 위에 있고, cli 에서는 늦게 부르나?**
> 이 모듈을 import 하는 순간 libmpv(공유 라이브러리)가 있어야 합니다. 그런데 인자
> 오류처럼 재생까지 안 가는 경우엔 libmpv 가 필요 없죠. 그래서 `cli.py` 는 Player 를
> **재생 직전에야** import 합니다(4.5). 덕분에 libmpv 없는 환경(CI 단위 테스트,
> Windows)에서도 cli·controller 같은 순수 로직을 import·테스트할 수 있습니다.

### 4.4 입력 → 동작 — `keyboard` → `Controller`  *(핵심)*

이제 사용자가 키를 누릅니다. 입력원(`keyboard.py`)의 심장은 **순수 함수** 하나입니다.

```python
_KEY_BINDINGS: dict[bytes, Action] = {
    b" ": Action.PAUSE,
    b"\x1b[C": Action.SEEK_FORWARD,   # → (방향키는 ANSI 이스케이프 시퀀스)
    b"\x1b[D": Action.SEEK_BACKWARD,  # ←
    b"\x1b[A": Action.VOLUME_UP,      # ↑
    b"\x1b[B": Action.VOLUME_DOWN,    # ↓
    b"m": Action.TOGGLE_MUTE,
    b"q": Action.QUIT,
    b"\x1b": Action.QUIT,             # 단독 Esc
}

def parse_key(data: bytes) -> Action | None:
    return _KEY_BINDINGS.get(data)
```

방향키는 한 글자가 아니라 `Esc [ C` 같은 3바이트 시퀀스로 들어옵니다. `parse_key` 는
이 바이트열을 추상 `Action` 으로 바꿉니다. **순수 함수**라 화면도 하드웨어도 필요 없어,
어느 OS에서나 테스트할 수 있습니다.

실제 터미널에서 키를 읽는 부분(`KeyboardInput`)은 리눅스 전용입니다.

```python
class KeyboardInput:
    def __enter__(self) -> KeyboardInput:
        import sys, termios, tty           # ← 사용 시점에만 import (플랫폼 격리)
        self._fd = sys.stdin.fileno()
        self._saved = termios.tcgetattr(self._fd)
        tty.setcbreak(self._fd)            # 원시 모드: 키 즉시 받기, 단 Ctrl+C 는 살림
        return self

    def __exit__(self, *exc) -> None:
        import termios
        termios.tcsetattr(self._fd, termios.TCSADRAIN, self._saved)  # 터미널 원복
```

> **왜 `termios` 를 함수 안에서 import 하나? / 왜 cbreak 인가?**
> `termios`·`tty` 는 리눅스에만 있는 모듈입니다. 파일 맨 위에서 import 하면 Windows/CI
> 에서 이 모듈을 *읽기만 해도* 터집니다. 그래서 **실제로 쓸 때(`__enter__`)** 에만
> 끌어옵니다 — 순수 로직(`parse_key`)은 어디서나 import 가능하게 둔 것이죠. 또
> 컨텍스트 매니저(`with`)로 만들어, 무슨 일이 있어도 `__exit__` 에서 **터미널 상태를
> 원복**합니다. 완전 raw 가 아니라 cbreak 를 쓴 이유는 `Ctrl+C`(SIGINT)를 살려 graceful
> 종료를 유도하기 위해서입니다.

이렇게 만들어진 `Action` 은 `Controller` 로 갑니다. Controller 는 동작별로 알맞은
Player 메서드를 부르고, **상태(일시정지 토글, 볼륨 값)** 를 관리합니다.
(`src/video_player/controller.py`)

```python
    def handle(self, action: Action) -> bool:
        if action is Action.PAUSE:
            self._toggle_pause()
        elif action is Action.SEEK_FORWARD:
            self._player.seek(self._config.seek_step_sec)     # +5초
        elif action is Action.SEEK_BACKWARD:
            self._player.seek(-self._config.seek_step_sec)    # -5초
        elif action is Action.VOLUME_UP:
            self._change_volume(self._config.volume_step)     # +5%
        ...
        elif action is Action.QUIT:
            self._player.quit()
            return False        # ← 루프에게 "이제 그만" 신호
        return True

    def _change_volume(self, delta: int) -> None:
        self._volume = _clamp(self._volume + delta, VOLUME_MIN, VOLUME_MAX)  # 0~100
        self._player.set_volume(self._volume)
```

- **일시정지는 토글**입니다. Controller 가 현재 상태(`self._paused`)를 기억하다가
  `pause()`/`resume()` 중 맞는 쪽을 부릅니다.
- **볼륨은 0~100 으로 클램프**합니다(부스트 없음). 이 산술은 순수해서 가짜 Player 로
  쉽게 검증됩니다.
- `QUIT` 만 `False` 를 돌려줍니다 — 재생 루프에게 멈추라는 신호입니다.

> **왜 Controller 가 `Player` 가 아니라 `PlayerLike`(Protocol)에 의존하나?**
> `controller.py` 는 mpv 를 모릅니다. 대신 "pause/resume/seek/… 메서드를 가진 무언가"
> 라는 인터페이스(`PlayerLike` Protocol)에만 의존합니다. 그래서 단위 테스트에서 호출을
> 기록하는 **가짜 Player** 를 끼워 넣어, libmpv 없이 "→ 키가 정말 `seek(+5)` 를 부르는가"
> 를 검증할 수 있습니다(의존성 주입). 이것이 분리막의 실질적 이득입니다.

### 4.5 재생 루프 — `cli.play`  *(핵심)*

부품이 다 모였습니다. `play()` 가 이들을 조립하고 재생 루프를 돌립니다.

```python
def play(path, config=None, *, player_factory=None, input_factory=None) -> int:
    config = config or Config()
    if player_factory is None:
        from video_player.player import Player   # ← 여기서야 libmpv 끌어옴
        player_factory = Player
    if input_factory is None:
        from video_player.keyboard import KeyboardInput
        input_factory = KeyboardInput

    player: Any = None
    try:
        with _stop_on_signals() as stop:
            player = player_factory(config)
            controller = Controller(player, config)
            player.load(path)                       # 자동 재생 시작
            _run_loop(player, controller, input_factory, stop)
        return EXIT_OK
    except DecodeError as exc:
        return exc.exit_code                        # 3
    except PlayerError as exc:
        return exc.exit_code
    finally:
        if player is not None:
            player.terminate()                      # mpv 자원 정리
```

`player_factory`/`input_factory` 인자가 보이시나요? 평소엔 진짜 `Player`/`KeyboardInput`
이 들어가지만, **테스트에서는 가짜를 주입**해 libmpv·터미널 없이 종료 코드 규칙을
검증합니다(5장). 이것도 의존성 주입입니다.

루프의 까다로운 점은 **두 가지를 동시에 기다려야** 한다는 것입니다: (a) 영상이 끝나는
것(EOF)과 (b) 사용자가 키를 누르는 것. `wait_for_playback()` 은 블로킹이라, 이것만
기다리면 키 입력을 못 받습니다. 그래서 EOF 대기는 **별도 스레드**에 맡깁니다.

```python
def _run_loop(player, controller, input_factory, stop) -> None:
    done = threading.Event()
    error: dict[str, DecodeError] = {}

    def _waiter() -> None:
        try:
            player.wait_for_playback()      # 끝까지 블록 (별도 스레드에서)
        except DecodeError as exc:
            error["decode"] = exc
        finally:
            done.set()                      # 끝났음을 알림
    waiter = threading.Thread(target=_waiter, daemon=True)
    waiter.start()

    with input_factory() as keyboard:
        while not done.is_set() and not stop.is_set():
            action = keyboard.read_action(timeout=_POLL_INTERVAL_SEC)  # 0.2초
            if action is None:              # 타임아웃(키 없음) → 종료 조건 재확인
                continue
            if controller.handle(action) is False:   # QUIT
                break

    player.quit()                           # 종료키/EOF 어느 경우든 mpv 정지 보장
    waiter.join(timeout=2.0)
    if "decode" in error:
        raise error["decode"]               # → play() 가 잡아 코드 3
```

- 키 읽기에 **0.2초 타임아웃**을 둔 이유: 입력이 없어도 주기적으로 깨어나 "영상이
  끝났나(`done`)? 종료 신호가 왔나(`stop`)?"를 확인하기 위해서입니다. 그래야 EOF 가
  나면 루프가 빠져나옵니다.
- **종료 경로가 셋**입니다: `q`/`Esc`(→ `handle` 이 `False`), 영상 끝(→ `done`),
  종료 신호(→ `stop`). 어느 쪽이든 루프를 벗어나 `player.quit()` 로 정리합니다.

신호 처리는 `_stop_on_signals` 컨텍스트 매니저가 맡습니다.

```python
@contextmanager
def _stop_on_signals() -> Iterator[threading.Event]:
    stop = threading.Event()
    previous: dict[int, Any] = {}
    def _request_stop(signum, frame) -> None:
        stop.set()                          # 신호 오면 루프 멈추라고 표시
    for sig in (signal.SIGINT, signal.SIGTERM):
        try:
            previous[sig] = signal.signal(sig, _request_stop)
        except (ValueError, OSError, AttributeError):
            pass                            # 메인 스레드 아님/미지원이면 건너뜀
    try:
        yield stop
    finally:
        for saved_sig, handler in previous.items():
            signal.signal(saved_sig, handler)   # 원래 핸들러 복구
```

> **왜 `SIGTERM` 까지 처리하나?**
> 지금은 `Ctrl+C`(SIGINT) 정도지만, 스펙은 앞으로 **프론트엔드가 이 플레이어를 자식
> 프로세스로 띄워** 종료시키는 상황을 내다봅니다. 그때 프론트가 보내는 `SIGTERM` 에도
> 깔끔히(터미널 원복 + mpv 정리) 끝나야 합니다. 핸들러를 끝에 **복구**하는 것도
> 매너입니다 — 라이브러리처럼 호출돼도 전역 상태를 더럽히지 않습니다.

**정리하면 종료 코드 한눈에:**

| 상황 | 어디서 | 종료 코드 |
|---|---|---|
| 정상 재생 끝 / `q`·`Esc` | `play` → `EXIT_OK` | 0 |
| 인자 없음 / 파일 없음·접근 불가 | `main`·`_validate_media_path` → `ArgumentError` | 2 |
| 깨진·디코드 불가 파일 | `Player.wait_for_playback` → `DecodeError` | 3 |

## 6. 설계 패턴 모아보기

4장에 흩어 둔 결정들을 패턴 이름으로 묶으면:

- **단방향 의존 (`입력원 → Controller → Player → mpv`)** — 의존이 한쪽으로만 흘러, 입력원
  교체가 쉽고 추론이 단순합니다.
- **분리막 (Controller)** — 입력원이 Player(=mpv)를 직접 못 만지게 가운데서 막습니다.
- **의존성 주입** — `play(player_factory=…, input_factory=…)`, `Controller(player, …)`.
  진짜 대신 가짜를 끼워 libmpv·터미널 없이 테스트합니다.
- **인터페이스로 의존 (Protocol)** — Controller 는 구체 `Player` 가 아니라 `PlayerLike`
  에 의존합니다.
- **플랫폼 경계 격리 + 지연 import** — `termios`(keyboard)와 `mpv`(player) 같은 플랫폼/무거운
  의존성은 **쓸 때만** 끌어옵니다. 순수 로직은 어디서나 import·테스트 가능.
- **순수 함수 분리 (`parse_key`)** — 부작용 없는 변환을 떼어내 테스트를 쉽게.
- **단일 책임** — 한 파일은 한 가지 일을 합니다(설정/상수/예외/로깅/입력/제어/엔진/조립).
