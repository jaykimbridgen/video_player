# 성능 · 자원 노트 (Performance & Resource Note)

> 영상 플레이어 파일럿 — 동영상 재생 성능과 CPU/메모리 자원 정책에 대한 기획 노트.
> 자체 완결적인 한 섹션이며, 추후 전체 문서 구조 확정 시 알맞은 위치에 편입한다.

## 0. 대상 환경 요약
- **H/W**: Dell 미니 PC (x86-64, Intel 내장 그래픽 가정)
- **OS**: Ubuntu Linux, **GUI 없는 헤드리스** 설치
- **재생 코어**: mpv / libmpv (내부적으로 FFmpeg 사용), DRM/KMS 직접 출력, HDMI로 영상+음성
- **현재 기기 성격**: 영상 재생 **전용** (다른 워크로드 없음)

## 1. 파일럿 기본 정책  **[구현 대상]**
재생 전용 기기이므로 **재생 매끄러움을 우선**하고 CPU 격리는 적용하지 않는다.

- **디코딩**: VA-API 하드웨어 디코딩 우선, 불가 시 소프트웨어(FFmpeg) **자동 폴백**.
- **프레임 드롭 활성화**: 부하 시 프레임을 떨궈 A/V 싱크 유지, 시스템 멈춤 방지. (mpv 기본값이 활성)
- **디코더 선행 버퍼(decode-ahead) 활성화**: 전용 기기 + 여유 RAM이므로 넉넉히 설정 (3절 참고).
- **재생 불가 파일**(깨짐/희귀 코덱)은 죽지 않고 **명확한 에러 로그 후 정상 종료**. (상세 동작은 '핵심 재생 기능' 항목에서 정의)

### 권장 mpv 설정 예시 (값은 구현 시 실제 기기에서 검증·조정)
```ini
hwdec=auto-safe          # HW 디코딩 가능 시 사용, 실패 시 SW 폴백
framedrop=vo             # 부하 시 프레임 드롭

# 디코더 선행 버퍼 — SW 디코딩 스파이크 흡수
vd-queue-enable=yes
ad-queue-enable=yes
vd-queue-max-secs=15
vd-queue-max-bytes=2000MiB

# 압축 데이터 읽기 캐시 — I/O 지터 완화 (CPU 부하와는 무관)
cache=yes
demuxer-max-bytes=512MiB
```

## 2. 디코딩 전략  **[구현 대상]**
- 소프트웨어 디코딩(FFmpeg)을 **만능 기본값**으로 둔다 — 사실상 모든 코덱 디코드 가능.
- VA-API 하드웨어 디코딩은 가능할 때만 사용해 CPU·전력 절감.
- 코덱별 HW 가속 가능 여부는 **CPU 세대에 의존** → CPU 모델 확인 필요 (6절).
- HW 디코딩 실패 시 자동으로 SW로 폴백되므로 **재생 자체는 보장**.

---

## 3. 디코더 선행 버퍼링 (decode-ahead) — 상세  **[구현 대상]**
**개념**: 디코딩한 프레임을 미리 RAM에 쌓아두고, CPU에 여유가 있을 때 버퍼를 채워, 무거운 구간에서는 버퍼에서 소비한다. → SW 디코딩의 **순간적 스파이크**를 흡수.

**전제 / 한계**
- 평균 디코딩 능력이 **실시간 이상**일 때만 효과가 있다. 평균이 모자라면 버퍼로도 못 구함 → HW 디코딩 / 해상도 down / 사전 트랜스코딩이 답.
- 비용은 **RAM**. 디코딩 프레임은 큼(1080p ≈ 3MB, 4K ≈ 12MB/장)이라 버퍼 시간 창은 메모리에 묶인다. mpv 기본 큐는 약 2초.
- HW 디코딩은 이 큐를 대부분 거치지 않는다(별도 `hwdec-extra-frames` 사용). → 이 카드는 **SW 폴백 상황 전용**.

**트레이드오프**: 추가 RAM 사용, 시작 시 버퍼 채우는 짧은 지연, seek 시 버려지는 프레임 약간(선형 재생엔 미미).

## 4. 미래 컨틴전시 — 다른 프로세스 추가로 CPU 경합 발생 시  **[추후 대비 · 구현 불필요]**
파일럿은 재생 전용이라 지금은 적용하지 않는다. 환경이 바뀌면 **약한 카드부터** escalation 한다.

| 방법 | 무엇을 하나 | 강도 | 도입 난이도 | 언제 쓰나 |
|---|---|---|---|---|
| HW 디코딩 보장 | VA-API로 흔한 코덱 HW 처리 | 근본 해결 | 낮음 | 항상 1순위 |
| 프레임 드롭 (`--framedrop`) | 부하 시 프레임 떨궈 싱크 유지 | 약 | 매우 낮음 | 기본 안전망 |
| 디코딩 스레드 제한 (`--vd-lavc-threads`) | 디코딩 코어 수에 상한 | 약~중 | 매우 낮음 | SW 디코딩이 코어 과점 시 |
| `nice` / `renice` | 플레이어 CPU 우선순위 낮춤 | 중 | 낮음 | 다른 프로세스가 가끔 우선이어야 할 때 |
| CPU 어피니티 (`taskset`) | 플레이어를 특정 코어에 고정, 나머지 코어 확보 | 강 (하드 격리) | 중 | 임계 프로세스에 코어 보장 |
| cgroups / systemd (`CPUQuota=`, `CPUWeight=`) | CPU 몫에 상한·가중치 부여 | 강 (유연) | 중 | 여러 서비스가 도는 기기 |
| 사전 트랜스코딩 | 유입 영상을 HW 친화 코덱으로 미리 변환 | 최강 | 높음 | 콘텐츠 유입을 통제할 수 있을 때 |

**Escalation 로직**: 필요한 만큼만 올라간다. 보통 *HW 디코딩 보장 + 프레임 드롭*으로 대부분 해결되며, 진짜 지연에 민감한 다른 프로세스가 생긴 시점에야 어피니티/cgroups로 격리를 추가한다.

## 5. 인접 미래 변수 (의식만 해둘 것)  **[추후 대비 · 구현 불필요]**
- **발열·스로틀링**: 4K SW 디코딩을 장시간 돌리면 온도 상승 → 성능 저하. 환기 확보·온도 모니터링으로 대응.
- **동시 다중 재생**: 화면 분할/멀티뷰로 범위가 커지면 디코딩 부하 배가, HW 디코딩 세션 수에도 한계.
- **메모리**: 영상 디코딩 자체는 RAM을 많이 쓰지 않음. 보통 CPU가 먼저 병목.
